# DataCube Product Continuity Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 先恢复可靠发布，再让 Oracle/PostgreSQL 用户在退出或意外中断后安全地继续 SQL 工作，最后用真实使用反馈确定复用功能的优先级。

**Architecture:** 按可独立验收的小阶段交付，不把 CI 修复、草稿存储、标签恢复和脚本管理合成一次大改。草稿与工作区只持久化编辑状态，沿用现有惰性连接及事务安全边界；各新功能先形成单独设计，经确认后编写逐文件实现计划。

**Tech Stack:** Java 25、JavaFX 25、JUnit Jupiter 5.11.3、Gradle wrapper 9.2.0、GitHub Actions；Windows 为正式发布平台，保留 Linux 自动化验证。

## Global Constraints

- 规划基线：`main` / `151a64a03ef66da44a88d72845484b89e46731d0`，2026-08-30 核对；执行每阶段前重新核对，不把旧统计当成新证据。
- `.testagent/` 属于用户，不读取、不修改、不暂存、不清理。
- 不访问公司数据库、现有 SQL 历史、真实凭据和已有业务导出；测试使用合成数据与独占临时目录。
- 用户批准本轮制定计划并分步推进，随后明确授权独立 worktree，任务完成后本地合并回 `main`；不自动授权推送、创建/删除 tag、发布 Release、联系用户或添加遥测。
- 2026-08-30 后续授权更新：用户确认列显示/隐藏增量，并明确“后续无需我确认，参照主流数据库开发管理工具来即可”。本路线图中常规设计、保存规则和交互选型的“确认”此后由代理记录决策并完成审查，不再等待逐项人工答复；真实数据库写入、外部通信、安装升级及推送发布的授权边界不变。
- 实现使用独立 worktree；`main` 仅准备 worktree 忽略规则，生产/测试修复在独立分支验证后合并。
- 草稿恢复不得自动连接、读取数据库元数据、执行 SQL、提交/回滚事务或重放任何 Redis 命令。
- 不保存数据库密码、API Key 配置、JDBC 会话对象、查询结果集或事务状态到恢复文件。SQL 文本本身可能含敏感信息，必须明确告知并提供关闭与清理机制。
- 恢复连接使用现有稳定 `ConnConfig.id()`；名称只用于展示，不以同名连接作为自动替代。
- 不默认上传 SQL、Schema、连接信息、文件内容或行为遥测。
- 文件失败必须保留可用旧版本并呈现失败状态；不能把内存更新、Base64 编码或普通写文件称作已安全持久化或加密。
- 每个实现任务都须有行为验证、差异审查和真实证据；未执行、失败、跳过、工具受限分别记录。
- 不把客户端防误操作措施描述为数据库权限控制或安全沙箱。

## 1. 当前事实与目标用户

面向日常使用 Oracle/PostgreSQL 查询、检查和导出数据的开发者，以及需要 Oracle → PostgreSQL 迁移的维护者。Redis 保持现有可用性，不纳入 SQL 恢复范围。

当前已经具备连接管理、独立 SQL 会话、风险确认、结果筛选与安全导出、迁移、Schema Diff。此次不以支持数量为目标，而以“完成一次工作”和“下次继续工作”为目标。

已核实：

1. [Verify run 33303961545](https://github.com/Clownking99/data-cube/actions/runs/33303961545)：Linux 单测、Redis 集成、wrapper validation 成功；Windows 单测失败。
2. 失败用例为 `SafeResultFilePublisherTest.successfulPublishAndCancellationHaveDifferentTerminalEffects`，原第 80 行。短路径临时目录可在本地复现相同断言失败；详细证据见本计划关联的 P0 计划。
3. `SqlHistoryStore` 最多保存 200 条近期记录，按 SQL 文本去重；执行时及正常关闭编辑器时已有历史快照。不是“未执行 SQL 从不保存”。
4. 历史记录按连接名称关联；新恢复功能必须独立使用连接 ID，不能照搬名称匹配。
5. 查询导出有自动化与部分桌面验收证据，但全部已加载范围切换、弹窗键盘、防抖边界以及真实 Excel 冻结/自动行高仍有未验收项。P0.2 续验发现缺少列隐藏入口，用户已批准补齐；实施与证据分别见[列控制计划](2026-08-30-result-column-visibility.md)及其后续验收记录，不用内部可见列契约冒充用户入口验证。
6. 当前没有本轮真实用户访谈、留存率或耗时基线；“恢复是最高价值新功能”是代码与工作流支持的产品假设，不是已测得的需求排名。

## 2. 方案选择与依赖

比较三种推进方式：

- **可靠发布 → 草稿 → 工作区 → 高频复用（推荐）**：每阶段能独立验收，先保护已有工作，再减少重复操作；需要明确恢复与隐私规则。
- 先做完整脚本项目/收藏系统：利于重度用户管理，但目录、外部修改、命名和文件冲突会扩大首期范围，不能替代异常退出保护。
- 先增加数据库或 AI 功能：扩大覆盖面，同时增加兼容性、凭据与维护成本；目前缺乏证据证明比核心工作连续性更急迫。

执行顺序：P0.1 CI 修复 → P0.2 发布验收 → P1 草稿恢复 → P2 工作区恢复 → P3 高频复用。P4 用户验证贯穿 P0.2、P1、P2，不等所有功能结束才收集反馈。

后续设计可以在发布动作等待授权时继续，但未通过发布验收的版本不得标记为稳定版；新交互须先记录设计决策与验证范围，再进入生产代码，常规选型按最新授权自主推进。

已完成且审查通过的独立产品增量可以按已有授权本地合并，不必等待推送/发布授权。发布验收中的未执行项继续保留，不能因本地合并改写为通过。

## 6. P1：SQL 草稿恢复（先设计，再独立实现）

**拟定职责边界：**

| 文件/区域 | 职责 |
| --- | --- |
| 新建 `src/com/datacube/config/SqlDraftStore.java` | 版本化、有限额的草稿持久化与加载结果；支持注入测试目录 |
| 新建 `src/com/datacube/fx/SqlDraftCoordinator.java` | 编辑事件防抖、串行写入、最新版本判定、状态通知及关闭生命周期 |
| `src/com/datacube/fx/SqlEditorPane.java` | 只捕获编辑状态与呈现保存状态，不在 FX 线程执行磁盘 I/O |
| `src/com/datacube/fx/AppShell.java` | 恢复入口及连接 ID 解析；不得在恢复时调用元数据或连接探测 |
| `src/com/datacube/config/AppSettings.java`、`src/com/datacube/fx/SettingsDialog.java` | 自动保存开关、保留策略与清理入口 |
| `test/com/datacube/config/SqlDraftStoreTest.java`、`test/com/datacube/fx/SqlDraftCoordinatorTest.java` | 持久化失败、版本竞争、清理竞争、生命周期与无数据库副作用 |

上述新增名称为本阶段的设计建议，不代表现有 API；经设计确认后，子计划必须给出确切签名和完整测试步骤。

- [ ] 写独立设计，比较“复用历史文件”和“独立草稿存储”；推荐独立存储，保留既有历史语义及文件，不自动迁移真实 SQL 历史。
- [ ] 确认保存规则：建议编辑停止 1 秒后保存，持续输入最多间隔 10 秒触发快照；这些是调度目标，不承诺磁盘拥塞或断电时零丢失。
- [ ] 确认隐私与容量规则：建议默认开启且首用明确告知、可关闭，7 天保留；上限与超限提示在设计中量化，不默默截断、丢弃当前草稿或无限写盘。
- [ ] 明确草稿设置与既有 SQL 历史的区别：关闭草稿保存不等于停止历史记录，清空草稿不等于清空历史或安全擦除磁盘；界面与帮助必须准确说明作用范围。
- [ ] 确认内容：草稿 ID、连接 ID、Schema 提示、SQL 原文、修改时间、格式版本；空白/Unicode/换行原样保存，不用历史的 `strip()` 语义。
- [ ] 确认生命周期：首次启用、用户主动关标签、正常退出、异常退出、恢复后再次编辑、清空、关闭自动保存分别定义是否留存，防止清空后后台旧任务又写回来。
- [ ] 确认多实例策略：使用单写者锁或独立实例命名空间，明确第二实例行为；不得让两个窗口互相覆盖恢复文件。
- [ ] 确认写入失败、损坏、未知版本、超限、存储禁用等状态；失败必须可见但不阻断继续编辑，不能虚假显示已保存。
- [ ] 设计评审后写独立实现计划，按“存储 → 调度 → UI 接入 → 恢复/清理”拆成各自可测试的任务。
- [ ] 验证普通保存、未执行文本、快速连续编辑、写入失败、异常退出、损坏恢复、多实例、关闭/清空竞态；恢复前后数据库连接/执行调用计数为零。
- [ ] 交付本地验收版本，明确自动保存窗口与已保存状态含义，不宣传绝对不丢数据。

恢复默认建议：启动时显示“发现可恢复草稿”，提供恢复、稍后、删除；不一启动就重建所有编辑器。按最新授权由代理在独立设计中确定交互并审查，不在 CI 修复或列控制中顺带实现。
