# G10 之后：维护成本整理

2026-10-09 维护者授权顺序为：独立完成 Redis 资源预算，再整理维护成本。此计划登记后续工作，不将仓库清理/架构重写塞进 G10。

## 目标和交付

把反复开发、验证、审查和接手的实际成本量化，给出可执行的优先级清单，并先落地低风险的文档/验证入口整理。历史失败和冻结证据保持可追溯，不以删测试、合并计数或缩减验收换取速度。

## 顺序

1. G10 P3 完成交付后建立新的 main 基线；只枚举允许的 src/test/buildSrc/docs/scripts 路径和明确排除 .testagent 的 Git 路径，不接触用户配置/业务文件。
2. 测量源码大类、关键模块调用/依赖、重复验证脚本、证据文件/字节规模、历史文档跳转和全量/CI 耗时。数字附采集脚本/范围/时间，不能只凭行数判坏代码。
3. 按“高频变更 × 出错影响 × 验证成本”排队：验证入口与证据索引、重复夹具/受控进程工具、AppShell/复杂 pane 的职责与生命周期边界、测试稳定性。Windows FX 初始化偶发超时保持根因未知，先诊断，不加长统一等待掩盖。
4. 先整理当前任务入口、验收证据索引和统一执行说明；提出新一轮可复用验证脚本的最小设计，确保环境隔离、实际 XML 统计、原日志哈希和首失败保留不退化。旧冻结脚本/日志只作为历史，不批量重写。
5. 单独给出可批准实施的架构拆分清单，每项写明问题、边界、候选接口、收益、迁移/回滚方式和必需回归。常规低风险整理可自主执行；历史证据删除/迁移、仓库历史重写、依赖升级或大规模架构改造不从“整理维护成本”推断授权。

## 约束与验收

- 不使用新业务功能作为维护性重构理由，不扩大 G8 外部验收。
- 不删历史测试、失败原件或已提交证据，不 git filter/reset/force-push，不操作 tag。
- 最终交付一份维护成本基线、优先级表（可复现问题、建议动作、影响范围、预期验证成本）、已实施整理和明确未实施项。
- 文档/索引整理验证链接与引用；脚本变更用独占临时 fixture 证明计数/失败/跳过/路径约束，避免为低影响文档更改重跑整个产品全量。
- 产品结构改动另按最小范围分批验证，保持 root 审查、唯一 Gradle 执行者和 main 精确 SHA 交付边界。
